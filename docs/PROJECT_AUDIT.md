**Критично для понимания:** идёт **параллельная миграция PHP → Go**. URL-контракты `/api/*.php` сохранены,
nginx через `location = /api/xxx.php` маршрутизирует конкретные endpoint'ы в Go (`127.0.0.1:8080`),
остальное попадает в PHP-FPM (`location ~ ^/api/(.+\.php)$`). То есть **для многих endpoint'ов существует
две реализации**, и они расходятся по правам доступа и поведению.

## 2. Краткая архитектура

```
Браузер (Vue SPA, dist/)
   │
   ├── /api/*.php ──► nginx
   │                   ├── allowlist `location = ...` ──► Go API :8080  (backend/)
   │                   └── fallback `location ~ ^/api/` ──► PHP-FPM    (api/)
   │                                    │
   │                                    └──► PostgreSQL corporate_portal
   ├── /img/*  ──► /var/lib/corporate-app/uploads/img/
   └── /       ──► dist/index.html (SPA fallback)
```

**Аутентификация:** логин/пароль → `POST /api/auth.php` → при отсутствии пользователя запрос в ASU
(`https://172.17.30.42/asu_lookup.php`) → создание записи в `user_info` → выдача `sessionToken`
(sha256-хэш в `user_sessions`) + httpOnly cookie `corp_session`. SPA хранит профиль в
`localStorage['auth-user']`, токен — в `localStorage['auth-session']`.

**Авторизация:** два уровня —
1. `user_group = 'admin'` — глобальный администратор;
2. групповые права по разделам: `portal_access_groups` → `portal_group_members` → `portal_group_permissions(section_key)`,
   плюс категории курсов `portal_group_course_categories`.

### SEC-001 — `/api/users.php`, `/api/profile.php`, `/api/forms*.php`, `/api/sync.php`, `/api/ofo*.php` доступны без аутентификации (Go API)

- **Severity:** Critical
- **Статус:** FIXED (VERIFIED на живом стенде)
- **Где:** `backend/cmd/api/main.go:37-46`; `backend/internal/handlers/users.go`, `profile.go`, `forms.go`, `sync.go`
- **Описание:** Обработчики собраны без поля `Auth`, и ни один не вызывает `requireUser/requireAdmin/requireSection`.
  nginx (`deploy/nginx-corporate.admsr.ru.conf:175,185`; `deploy/nginx-go-api-wave2.conf`) публично проксирует эти пути в Go API.
- **Доказательство (чтение кода):**
  - `users.go:13-15` — `type Users struct { Pool *pgxpool.Pool }`, поля `Auth` нет;
  - `users.go:28-105` — `GET` возвращает **все** строки `user_info`, включая колонку `password`;
  - `users.go:124-161` — `PUT ?id=N` обновляет произвольные поля, включая `password`, `user_group`, `status`;
  - `profile.go:104-141` — `POST` берёт `id` из тела и пишет в `user_info` без проверки личности;
  - `sync.go:17-66` — `POST` создаёт пользователя с произвольным `id`/`login`/`password` без общего секрета;
  - `forms.go` (1383 строки) — `grep -c 'RequireUser|requireAdmin|requireSection'` → 0.
- **Последствия:** утечка всех учётных данных → вход под любым сотрудником; повышение привилегий до `admin`
  одним `PUT`; создание собственного пользователя через `sync.php`; чтение/удаление всех форм и ответов.
- **Воспроизведение (ВЫПОЛНЕНО на живом стенде, тестовая БД доступна):**
  `GET http://127.0.0.1:8080/api/users.php` без заголовков → **HTTP 200**, JSON с **30 пользователями,
  из них 9 с `user_group=admin`, и все 30 паролей — в открытом виде** (0 bcrypt-хэшей).
  `GET /api/profile.php?id=1` → **200**, утечка ФИО/email/телефона администратора.
- **Исправление (Go, PHP не трогаем далее по решению владельца):**
  - `users.go` — `Auth` в структуре, `requireAdmin` в `ServeHTTP`; колонка `password` убрана из SELECT и из ответа;
    в `PUT` пароль хэшируется `bcrypt`, пустая строка = «не менять».
  - `profile.go` — `requireUser` на чтение; запись только владельцу либо админу (проверка `id == cur.ID`).
  - `forms.go` — добавлены `formsRequireUser`/`formsRequireEditor`; расставлены по `Forms`/`List`/`Publish`/`Report` и т.д.
  - `sync.go` — обязательный общий секрет `X-Sync-Secret` (сравнение `subtle.ConstantTimeCompare`).
  - `ofo.go` — `requireUser` на все методы.
  - `main.go` — `Auth`/`Config` проброшены во все перечисленные хендлеры.
- **Как проверено:**
  - Live A/B: исправленный API на `:8090` отдаёт **401** на все перечисленные анонимные запросы (было 200/создание).
  - Регрессионные тесты Go: `TestEndpointsRequireSessionBeforeTouchingDB` (14 кейсов), `TestSyncRequiresSharedSecret`,
    `TestSyncRejectsWhenSecretNotConfigured`. Тесты **падают на старом коде** (nil-pool паника = проверка пропущена)
    и **проходят на новом** — доказано снятием guard'а и повторным прогоном.
  - `go build ./...`, `go vet ./...`, `go test ./...` — зелёные.

### SEC-006 — Полный обход аутентификации: `session_bootstrap` выпускал сессию любого пользователя по `id` из тела

- **Severity:** Critical
- **Статус:** FIXED (VERIFIED)
- **Где:** `backend/internal/handlers/auth.go:200` (`SessionBootstrap`)
- **Описание:** `POST /api/session_bootstrap.php` с телом `{"id": N}` выпускал валидный `sessionToken` для любого
  пользователя, у которого `auth=true` и `last_activity` в пределах 24 ч, **без какого-либо доказательства личности**.
  В связке с SEC-001 (список id всех админов открыт) → выпуск себе админской сессии → полный захват.
- **Последствия:** обход аутентификации и повышение привилегий до `admin`.
- **Исправление:** личность берётся только из действующей сессии (`CurrentUser`); `id` из тела допускается лишь
  если совпадает с текущим пользователем, иначе 403. Тот же принцип продублирован в PHP-версии (`api/session_bootstrap.php`)
  и убрано зеркалирование произвольного `Origin` с `Allow-Credentials`.
- **Как проверено:**
  - Регрессионный тест `TestSessionBootstrapRejectsBodyIDWithoutSession` — **падает на старом коде** (доходит до
    запроса в БД без проверки сессии), **проходит на новом**. Плюс `TestSessionBootstrapRejectsNonPost`.
  - Live: исправленный API на `:8090` отдаёт 401 на `{"id":1}` без токена.

### BUG-001 — Переключение статуса пользователя не откатывается при ошибке сервера

- **Severity:** Medium
- **Статус:** FIXED
- **Где:** `src/pages/Admin/AdminDashboardPage.vue` — `toggleUserStatus`
- **Описание:** оптимистичное обновление статуса откатывалось только в `.catch` (сетевая ошибка).
  HTTP 401/403/500 и `{success:false}` не реджектят `fetch`, поэтому UI показывал новый статус,
  хотя сервер запрос отклонил. С ужесточением авторизации (теперь 403/401 реальны) баг стал проявляться.
- **Последствия:** рассинхрон UI и БД — админ видит «Заблокирован», а в БД пользователь активен (или наоборот).
- **Исправление:** проверка `res.ok` и `json.success`, откат к прежнему статусу при любой неуспешности.
- **Как проверено:** сборка фронта (`npm run build`) — зелёная; ручной разбор ветвей ошибок.

### BUG-002 — Редактирование пользователя не откатывается при ошибке сервера

- **Severity:** Medium
- **Статус:** FIXED
- **Где:** `src/pages/Admin/AdminDashboardPage.vue` — `saveEdit`

### UX-001 / ARCH-001 — Рассинхрон «UI залогинен ↔ сессия истекла» → повторяющаяся ошибка «Требуется авторизация»

- **Severity:** Medium
- **Статус:** FIXED (реализованы варианты «а» и «б»)
- **Что сделано:**
  - **Единый обработчик 401** (`useAuthSession.setUnauthorizedHandler`, вызывается из `apiSessionFetch`/
    `apiSessionUpload`): при недействительной сессии после одной попытки восстановления — чистый выход
    на `/login` с сообщением «Сессия истекла. Войдите снова.» вместо повторяющейся ошибки. Регистрируется
    в `useSessionActivity` (`forceLogout`). Важно: реагирует только на **401** (нет сессии); **403**
    (нет прав) не трогает — пользователь остаётся залогинен.
  - **Скользящее продление сессии** (`backend/internal/auth/session.go:CurrentUser`): каждый авторизованный
    запрос сдвигает `expires_at` на полный TTL. Активный пользователь больше не «отваливается» посреди
    работы; по-настоящему простоявшая дольше TTL сессия честно истекает.
  - `session_bootstrap` опознаёт пользователя по cookie `corp_session`, поэтому потеря только localStorage-токена
    восстанавливается автоматически (без реоткрытия дыры SEC-006).
- **Как проверено:** `go build/vet/test` и `npm run build` зелёные; на dev-стенде переход на защищённый
  маршрут без сессии даёт чистый редирект на вход (не всплывающую ошибку).
- **Где:** `src/router/index.js` (`checkAuthInDb`), `src/composables/useSessionActivity.ts`,
  `backend/internal/handlers/auth.go` (`CheckAuth`, `Heartbeat`, `CreateSession`)
- **Описание:** router-guard и авто-логаут проверяют `check-auth.php` по `id` (флаг `user_info.auth`
  и `last_activity < 24ч`), **не** проверяя сам токен сессии. Токен сессии имеет фиксированный TTL 24ч
  от момента создания (`CreateSession`, не скользящий). Активный пользователь по истечении 24ч сохраняет
  «залогиненный» UI (heartbeat держит `last_activity` свежим, флаг `auth` = true), но все API-вызовы,
  требующие сессию (после SEC-001/009 их стало больше), возвращают 401, а приложение не предлагает войти заново.
- **Последствия:** после ~24ч непрерывной работы данные перестают грузиться (401) без внятного авто-редиректа на вход.
- **Рекомендация (не внесено — требует решения по auth-модели, риск регрессий):** один из вариантов —
  (а) глобально трактовать 401 от API как невалидную сессию → `forceLogout`;
  (б) продлевать `expires_at` сессии на heartbeat (скользящее окно);
  (в) в `check-auth.php` валидировать токен сессии, а не только флаг `auth`.
- **Почему не исправлено сейчас:** затрагивает контракт аутентификации многих потоков; приоритет отдан
  устранению 5 Critical-дыр. Зафиксировано как известное ограничение для отдельной итерации.

### SEC-005 — Вход по паролю в открытом виде (fallback `$user['password'] === $password`)

- **Severity:** High
- **Статус:** CONFIRMED (VERIFIED на живом стенде: 30/30 паролей в БД — открытый текст, 0 bcrypt)
- **Где:** `api/auth.php:166`; тот же fallback в Go `auth.go:passwordOK`
- **Описание:** если в БД пароль хранится не хэшем, сравнение идёт в открытом виде. `sync.php` и ASU кладут пароль «как есть».
- **Последствия:** пароли сотрудников хранятся в БД открытым текстом и отдаются через `users.php` (см. SEC-001).
- **Предлагаемое исправление:** миграция на `password_hash()`; как минимум — не отдавать пароль в API.
