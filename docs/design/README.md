# Дизайн-документация

Описывает **фактический** интерфейс портала, восстановленный по коду экранов, а
не желаемый. Единой формализованной дизайн-системы в проекте нет — есть
устойчивые паттерны поверх Nuxt UI. Здесь они зафиксированы; отклонения вынесены
отдельно.

## Порядок работы над UI-задачей

1. **Прочитать [tokens.md](tokens.md)** — цвета, шрифты, радиусы, темы. Не
   вводить собственные значения, если есть токен.
2. **Прочитать [layout-and-navigation.md](layout-and-navigation.md)** — каркас
   страницы стандартизован, новую страницу собирать по нему.
3. **Найти готовое в [components.md](components.md)** — сначала компонент
   проекта, затем компонент Nuxt UI, и только потом новый.
4. **Свериться с API Nuxt UI** — [nuxt-ui.md](nuxt-ui.md) описывает, как это
   делать (MCP Nuxt UI в текущей сессии недоступен, см. там же).
5. **Взять состояния из [states-and-feedback.md](states-and-feedback.md)** —
   загрузка, пусто, ошибка, успех, запрет.
6. **Не «чинить» отклонения попутно** — проверить
   [inconsistencies.md](inconsistencies.md); там же предложения по унификации,
   которые требуют отдельного решения.

## Что считать правилом, а что — случайностью

Правилом в этих документах названо только то, что повторяется во многих местах и
подтверждено подсчётом. Единичное отличие одного экрана правилом не объявляется —
оно попадает в [inconsistencies.md](inconsistencies.md).

Везде, где приводятся числа («238 вхождений», «~22 файла»), это **снимок** grep'а
по `src/` на 2026-09-22. Код активно меняется — точные значения расходятся со
временем, соотношение между ними остаётся показательным. Пересчитать можно
командами вида:

```bash
grep -rho 'text-muted' src/ --include=*.vue | wc -l
```

## Ограничение

Документирование **не меняет интерфейс**. Все найденные отклонения только
зафиксированы.
