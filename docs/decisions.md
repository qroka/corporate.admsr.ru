# Журнал архитектурных решений (ADR)

Фиксируются только **подтверждённые** решения: те, что видны в коде, конфигурации,
комментариях, README или аудите. Если причина решения нигде не зафиксирована —
так и написано, домыслы не добавляются.

Формат записи: контекст → решение → подтверждение → следствия.

---

## ADR-001. Параллельная миграция PHP → Go с сохранением URL `/api/*.php`

- **Статус:** действует
- **Решение:** новый backend пишется на Go, но URL-контракты `/api/<имя>.php`
  не меняются. Переключение — точным allowlist'ом nginx
  (`location = /api/<файл>.php` имеет приоритет над регуляркой PHP).
- **Подтверждение:** `backend/README.md` («Vue SPA без изменений… nginx
  переключает маршруты точным allowlist»), `deploy/nginx-corporate.admsr.ru.conf:55-56`,
  `backend/cmd/api/main.go`.
- **Причина (подтверждена):** не менять фронтенд при переносе backend.
- **Следствия:** три списка путей (Go mux, nginx, Vite proxy) нужно держать
  синхронными; для многих эндпоинтов существуют две реализации.
- **Правило переноса, зафиксированное в `backend/README.md`:**
  handler → smoke → nginx allowlist → наблюдение → удаление PHP только после стабилизации.

## ADR-002. PHP-слой заморожен; правки backend — только в Go

- **Статус:** действует с 2026-09-21
- **Решение:** `api/` не изменяется; киоск (`src/pages/Kiosk/`, `AppKiosk`) не
  трогаем. Уже внесённые точечные правки в PHP оставлены как есть.
- **Подтверждение:** `docs/PROJECT_AUDIT.md`, §8 «Решение владельца (2026-09-21)».
- **Следствия:** проблемы SEC-002…SEC-005 остаются открытыми осознанно;
  новая функциональность backend пишется только на Go.

## ADR-003. Личность пользователя берётся только из серверной сессии

- **Статус:** действует
- **Решение:** ни `userId` из тела запроса, ни заголовок `X-User-Id` не являются
  источником личности. Только `auth.Service.CurrentUser` по токену сессии.
- **Подтверждение:** `backend/internal/auth/session.go:159-201`;
  `tests_routes.go` (`viewer()`); `forms.go` (`formsRequireUser`/`formsRequireEditor`);
  `PROJECT_AUDIT.md`, SEC-006/007/008.
- **Причина (подтверждена):** клиентские идентификаторы подделываются — это
  приводило к полному обходу авторизации.
- **Следствия:** клиентский код, всё ещё отправляющий `userId`, — рудимент
  (см. [known-issues.md](known-issues.md), IMP-13). `owner_id IS NULL`
  трактуется как «доступ запрещён».

## ADR-004. Двухканальная передача токена: cookie + Bearer

- **Статус:** действует
- **Решение:** при входе выдаются одновременно httpOnly-cookie `corp_session` и
  `sessionToken` в теле. Сервер принимает `Authorization: Bearer` →
  `X-Session-Token` → cookie в этом порядке.
- **Подтверждение:** `backend/internal/auth/session.go:60-73,108-126`;
  `src/composables/useAuthSession.ts`.
- **Причина (подтверждена частично):** комментарий в `useAuthSession.ts:1-4` —
  «Используется модулем курсов; не ломает legacy API, которые ещё принимают
  userId». То есть Bearer вводился под модуль курсов, cookie осталась для
  легаси-вызовов. Почему не унифицировали позже — **[НЕИЗВЕСТНО]**.

## ADR-005. Проверка прав внутри хендлеров, без middleware

- **Статус:** действует
- **Решение:** `mux.Handle(path, handler)` без цепочек; guard
  (`requireUser`/`requireAdmin`/`requireSection`) вызывается первой строкой
  каждого метода.
- **Подтверждение:** `backend/cmd/api/main.go`, `backend/internal/handlers/section.go`.
- **Причина:** **[НЕИЗВЕСТНО]** — в коде не зафиксирована.
- **Следствия:** забыть guard легко; именно так возникли SEC-001/009. Отсюда
  требование покрывать новые эндпоинты тестом вида
  «аноним → 401 до обращения к БД» (`auth_guards_test.go`).

## ADR-006. Права по разделам через группы портала, плюс суперадмин

- **Статус:** действует
- **Решение:** два независимых уровня — `user_info.user_group = 'admin'`
  (всё) и членство в `portal_access_groups` с правами на `section_key`.
  Для курсов — дополнительное сужение по категории.
- **Подтверждение:** `db/migration/V5`, `V6`; `backend/internal/auth/permissions.go`;
  `src/composables/useSectionAccess.ts`.
- **Следствия:** список секций продублирован во фронте и в Go; синхронизация ручная.

## ADR-007. UI-тоггл роли отделён от прав

- **Статус:** действует
- **Решение:** `localStorage['ui-role']` переключает отображение админ-функций.
  Для суперадмина `canEdit` требует `currentRole === 'admin'`; на права
  обычного пользователя тоггл не влияет.
- **Подтверждение:** `src/stores/role.js`, `src/composables/useSectionAccess.ts:110-118`,
  `src/components/AppHeader.vue:48-58`, `src/router/index.js:280-286`.
- **Причина (выводится из кода):** возможность посмотреть портал глазами
  сотрудника. Явной формулировки в коде нет — **[ЧАСТИЧНО]**.
- **Следствия:** роль в localStorage не является защитой; сервер её не читает.

## ADR-008. Киоск работает без авторизации и без админ-функций

- **Статус:** действует
- **Решение:** ветка `/kiosk` доступна анонимно; роль принудительно `user`;
  `requiresAdmin`/`requiresSection` внутри киоска → редирект на `/kiosk`;
  переходы на «обычные» маршруты из киоска перенаправляются на киоск-аналоги
  **до** проверки авторизации.
- **Подтверждение:** `src/router/index.js:243-277`, комментарий в коде:
  «киоск работает полностью без входа».

## ADR-009. Тема как набор CSS-переменных, применяемых из JS

- **Статус:** действует
- **Решение:** полные палитры Tailwind объявлены в `:root`
  (`src/assets/tailwind.css`), а `applyUiTheme()` копирует выбранную палитру в
  переменные Nuxt UI (`--ui-color-primary-*`, `--ui-color-neutral-*`, `--ui-primary`)
  и задаёт `--font-sans`, `--ui-radius`, `data-ui-font`.
- **Подтверждение:** `src/composables/useUiTheme.ts:186-224`; комментарий там же:
  «Tailwind v4 exposes palette steps as CSS vars… We mirror them into Nuxt UI vars».
- **Причина (подтверждена комментарием в CSS):** палитры объявлены как `:root`,
  «so they are never tree-shaken by Tailwind».
- **Следствия:** доступны 18 primary и 9 neutral цветов, 4 шрифта, 5 радиусов;
  тема применяется до монтирования приложения (`src/main.js`), чтобы не было
  мигания.

## ADR-019. Миграции идемпотентны, без таблицы версий

- **Статус:** действует
- **Решение:** весь SQL пишется как `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`;
  `deploy.sh` прогоняет **все** `V*.sql` при каждом деплое.
- **Подтверждение:** `deploy/deploy.sh:247-259`, текст миграций.
- **Следствия:** новая миграция **обязана** быть идемпотентной, иначе деплой
  сломается на втором запуске.

## ADR-020. Недействительная сессия → единый выход, а не ошибка в интерфейсе

- **Статус:** действует с коммита `bcd9d95` (2026-09-22)
- **Решение:** если авторизованный запрос вернул 401 и повторная выдача токена
  не помогла, приложение один раз уводит пользователя на `/login` с пометкой
  «Сессия истекла», вместо того чтобы показывать ошибку на каждом запросе.
- **Подтверждение:** `src/composables/useAuthSession.ts:64-93,186-191,209-221`
  (комментарий: «Это убирает повторяющуюся ошибку „Требуется авторизация“:
  вместо неё пользователь один раз чисто уводится на страницу входа»);
  `src/composables/useSessionActivity.ts:57-61`; `src/pages/login.vue:28-34`.
- **Причина (подтверждена комментарием):** UX-001 — при истёкшей сессии
  интерфейс выглядел залогиненным и сыпал ошибками.
- **Связанное решение того же коммита:** TTL сессии сделан **скользящим** —
  `CurrentUser` при каждом авторизованном запросе сдвигает `expires_at` на
  полный TTL (`backend/internal/auth/session.go:194-205`). Причина
  (подтверждена комментарием): активный пользователь не должен «отваливаться»
  посреди работы, а реально простоявшая сессия истекает честно.
- **Следствия:** обработчик регистрируется один раз при старте
  (`startSessionActivity`); повторные срабатывания подавляются флагом
  `unauthorizedFired` (сброс через 5 с). Остаток: `check-auth.php` всё ещё
  проверяет флаг `auth`, а не токен.

## ADR-021. «Управление обучением» — отдельная страница, а не вкладка

## ADR-022. Разделители и рамки на `bg-elevated` — `*-accented`

- **Статус:** действует с 2026-09-22
- **Решение:** внутри карточек и панелей с фоном `bg-elevated` рамки и
  разделители — `border-accented` / `ring-accented`, не `*-default`.
- **Подтверждение:** `node_modules/@nuxt/ui/dist/runtime/index.css` — в тёмной
  теме `--ui-bg-elevated` и `--ui-border` оба равны `neutral-800`, а
  `--ui-border-accented` — `neutral-700`.
- **Причина (подтверждена):** `border-default` на `bg-elevated` в тёмной теме
  совпадает с фоном — разделитель невидим (замечено владельцем).
- **Следствия:** на фоне страницы (`bg-default`) `*-default` по-прежнему
  годится. Hover-подсветка внутри `bg-elevated` — `bg-accented/40`, а не
  `bg-elevated/…` (иначе эффекта нет).

## ADR-023. Мастер создания курса — сквозные «Шаг N из 4»

- **Статус:** действует с 2026-09-22
- **Решение:** создание курса (1) → тема (2) → материал (3) → тест темы (4);
  баннеры и тосты между шагами используют одну нумерацию. Флаг режима — `?guide=1`.
- **Подтверждение:** `CourseCreatePage.vue`, `TopicFormPage.vue`,
  `MaterialFormPage.vue`, `CourseAdminTestPage.vue` (строки «Шаг N из 4»).

  участвовал, но его тост говорил «Шаг 1», и следующий экран встречал вторым
  «Шагом 1 из 3».

## ADR-024. Засчёт времени: файлы и ссылки — без требования фокуса

- **Статус:** действует с 2026-09-24
- **Решение:** heartbeat для `rich_text` идёт, только если вкладка портала
  активна и было действие за 30 с; для файлов и ссылок — пока материал открыт
  и вкладка портала не закрыта.
- **Подтверждение:** `shouldBeat()` в `src/pages/Courses/employee/CourseMaterialPage.vue` (до ADR-034 — `CourseTopicPage.vue`).
- **Причина (подтверждена владельцем):** файлы и ссылки открываются в новой
  вкладке; при требовании фокуса время на них не шло вовсе, и материал с
  минимальным временем нельзя было пройти, читая его (IMP-20).
- **Следствия:** защита от накрутки — только серверная: `MaterialHeartbeat`
  не засчитывает паузы длиннее 90 с и не добавляет больше 60 с за раз.

## ADR-025. `NextAction` сам завершает «созревшие» темы и не обрывается на просрочке

- **Статус:** действует с 2026-09-24
- **Решение:** (1) если условия темы выполнены, а статус не `completed`,
  `NextAction` завершает тему, пересчитывает блокировки и вычисляет шаг заново;
  то же делает `MaterialHeartbeat` после каждого засчитанного интервала.
  (2) Для `overdue` вычисляется реальный следующий шаг.
- **Подтверждение:** `markTopicCompleted`, `CompleteTopicIfReady`, `NextAction`
  в `backend/internal/courses/common.go`; `MaterialHeartbeat` в
  `backend/internal/handlers/courses.go`.
- **Причина (подтверждена владельцем):** IMP-18, IMP-19 — сотрудник упирался в
  тупик и не мог пройти курс.
- **Следствия:** `NextAction` — чтение **с побочным эффектом** (как и раньше:
  он уже вызывал `RecalculateLocks`). Рекурсия ограничена числом тем:
  повторный вызов происходит, только если `UPDATE` реально изменил строку.

## ADR-026. Порядок тем — перетаскиванием на `vuedraggable`

- **Статус:** действует с 2026-09-24

  `i-lucide-grip-vertical`; стрелки остались в меню `⋯` для клавиатуры и тача.

- **Подтверждение:** `applyOrder()` в

  `vuedraggable@4.1.0` уже был в зависимостях. Новых библиотек не добавлялось.

## ADR-027. Адаптивность шапки — container queries, а не брейкпоинты окна

- **Статус:** действует с 2026-09-24
- **Решение:** корень шапки помечен `@container`; вариант кнопки поиска
  выбирается по ширине шапки (`@4xl` = 56rem, `@6xl` = 72rem): иконка →
  «Поиск…» → полная подпись.

## ADR-032. Данные сотрудника — один источник: `user_info`

- **Статус:** действует с 2026-09-28
- **Решение:**
  - журнал отсутствия получает ФИО, ОФО и должность с сервера из `user_info`
    (POST игнорирует их в теле) и показывает текущие данные сотрудника
    (`absenceView` в `backend/internal/handlers/absence.go`); копия в записи —
    на случай, если сотрудника уже нет;
  - подразделения везде — дерево `ofo_unit`; журнал больше не читает легаси `ofo.php`;
  - ОФО и должность заполняются одним компонентом `UserWorkFields.vue` в
    профиле, онбординге и админке;
  - имя — `userFullName` / `userShortName` (`src/utils/userName.ts`);
  - профиль не хранит копию имени и аватара в `localStorage`.
- **Причина:** по жалобе владельца на расхождения. Найдено: журнал брал
  ФИО/ОФО/должность из снимка `auth-user` на момент входа (после правки профиля
  расходились, а сотрудник мог прислать любые значения); подписи ОФО журнала
  шли из таблицы `ofo`, а `user_info.ofo` ссылается на `ofo_unit`; в админке
  ОФО вводили номером, а должность — текстом; при открытии профиля должность,
  которой нет в справочнике, стиралась; шапка при пустой должности показывала
  `user`/`admin` или «Инженер»; копия аватара в `localStorage` переходила к
  следующему пользователю браузера.
- **Следствия:** если сотрудника перевели, его прошлые отсутствия показываются
  с новым ОФО и попадают в фильтр нового подразделения. Отметить отсутствие без
  ОФО и должности в профиле нельзя (422 с подсказкой).

## ADR-033. Реакции на новости — на сервере, по сотруднику

- **Статус:** действует с 2026-09-28
- **Решение:** таблица `news_reactions (news_id, user_id, reaction)` (V11), PK по
  тройке — одна реакция каждого вида на сотрудника, несколько разных можно.
  8 реакций, список в коде (без CHECK — добавление не требует миграции).
  Поставить/снять — `POST news.php?id=…&action=react {reaction, active}` только
  с сессией; кто отреагировал — `GET …&action=reactors&reaction=…` (для вошедших).
  Старый `action=like` оставлен как синоним реакции «like».
- **Причина:** задача владельца «реализовать систему реакций полностью». Было:
  лайк — анонимный счётчик `news.likes` без входа, отметка «я лайкнул» — в
  `localStorage` (с другого браузера лайк ставился повторно, «снять» уменьшало
  чужие), ❤️ и 🙂 показывали заглушку.
- **Следствия:** `news.likes` больше не меняется и прибавляется к счётчику «like»
  как накопленные до реакций анонимные лайки — иначе на проде обнулились бы
  существующие цифры; снять их нельзя. В киоске реакции не показываются
  (как и раньше лайк).

## ADR-034. Материал курса — на своей странице, файлы показываются встроенно

- **Статус:** действует с 2026-09-28
- **Решение:** маршрут `course-material`
  (`/courses/:enrollmentId/topics/:topicId/materials/:materialId`,
  `src/pages/Courses/employee/CourseMaterialPage.vue`); страница темы стала
  оглавлением. PDF — `<iframe>` со встроенным просмотрщиком браузера, видео —
  `<video>`, изображения — `<img>`; прочие файлы — «Скачать». Вид определяется по
  MIME, при его отсутствии — по расширению (`courseMaterialView.ts`). Heartbeat
  переехал на страницу материала; правило ADR-024 сохранено.
  С 2026-09-29 переход к следующему шагу из курса или после теста ведёт на
  страницу темы, а не сразу в материал (просьба владельца).
- **Причина:** задача владельца: «просмотр PDF и видео прямо на странице с
  материалами; один материал — одна страница». Раньше все материалы темы были на
  одной странице, файлы открывались в новой вкладке.
- **Следствия:** PDF показывает сам браузер — в Chrome/Edge/Firefox/Яндекс на
  компьютере работает; где просмотрщика нет (`navigator.pdfViewerEnabled ===
  false`, напр. Android) — вместо фрейма кнопки «Открыть»/«Скачать». Единый вид на
  всех устройствах дала бы pdf.js — это новая зависимость, не вводилась.
  Файлы отдаются по cookie сессии (фрейм и плеер не шлют `Authorization`).

## ADR-036. Назначения на ОФО и «всем» — постоянные

- **Статус:** действует с 2026-09-28
- **Решение:** цель `all` (V12) и досоздание записей по действующим назначениям
  `ofo`/`all` опубликованных версий — `courses.Service.SyncStandingAssignments`
  (`backend/internal/courses/assign.go`), вызывается при входе (`auth.go`),
  сохранении профиля (`profile.go`) и в `courses_for_me`. Ранее отменённая
  администратором запись по тому же назначению не восстанавливается. Срок «N дней»
  хранится в назначении (`deadline_days`) и считается от момента выдачи.

  назначенные на это ОФО, в том числе давние; перестать выдавать — снять курс с
  публикации (отмены назначения целиком в интерфейсе нет). Назначение на
  пользователя по-прежнему разовое. Без миграции V12 «всем» отвечает 503.

## ADR-037. «Назад» в тесте есть всегда, пропущенный вопрос не фиксируется

- **Статус:** действует с 2026-09-29
- **Решение:** `src/pages/Tests/TestRunner.vue` (общий для тестов курса и
  модуля `/tests`): кнопка «Назад» показывается всегда (кроме истёкшего
  времени и подсветки ответа); «Далее» фиксирует только **данный** ответ —
  пропущенный вопрос остаётся открытым. Менять данные ответы при возврате можно
  только с «Разрешить изменять ответ» (`allowChangeAnswer`), иначе вопрос
  показывается как «Ответ зафиксирован» с кнопкой «Дальше». Настройка
  «Свободный переход между вопросами» (`freeNavigation`) больше ни на что не
  влияет и убрана из конструкторов; в конструкторе теста курса на её месте —
  «Разрешить менять ответы до завершения». Поле в БД и API осталось.
- **Причина:** баг-репорт владельца 2026-09-29: «есть кнопка далее, но нет
  назад»; «завершил тест, не ответив на все вопросы, — возвращает к вопросам,
  но ответить нельзя». Второе — дефект: `lockCurrentIfNeeded` фиксировал
  вопрос при «Далее» без ответа.
- **Следствия:** у форм модуля `/tests`, где «Свободный переход» был выключен,
  тоже появился «Назад» (только просмотр данных ответов).

## ADR-038. Онбординг: шаг «Внешний вид», масштаб — подсказкой про Ctrl +/−

- **Статус:** действует с 2026-09-29
- **Решение:** между аватаром и итогом добавлен компактный шаг «Внешний вид» (`OnboardingPage.vue`): строка
  «Подберите масштаб: Ctrl + / Ctrl −» (масштаб браузера) и ряды выбора — тема (светлая / тёмная), цвет, шрифт,

- **Причина:** просьба владельца 2026-09-29: рассказать про настройку темы и предложить пользователю самому настроить

## ADR-039. Типы вопросов «Соответствие» и «Классификация»

- **Статус:** действует с 2026-09-29
- **Решение:** `match` (понятие → определение) и `classify` (утверждение → категория) — один вопрос, у которого
  каждому элементу слева выбирается один вариант справа. Хранение в `test_options` с `role` и `target_option_id`
  (V13), ответ — JSON `{itemId: targetId}` в `test_answers.text_value`; ключ клиенту — `correct: {itemId: targetId}`.
  Оценка: один вопрос — один балл, засчитывается только если верны все соответствия (`tests.ScorePairing`; сначала
  считали по парам, владелец 2026-09-30 потребовал «один вопрос — один балл»). У `match` определения на клиенте
  всегда перемешиваются, допустимы лишние определения. Прохождение — перетаскиванием карточек (`vuedraggable`, уже
  в зависимостях): `match` — определение в ячейку понятия (в ячейке одно, прежнее возвращается к остальным),
  `classify` — утверждение в колонку категории; нажатие на разложенную карточку возвращает её.
  **С клавиатуры (с 2026-10-01, IMP-60):** Enter/Пробел на карточке из общего набора выбирает её, затем кнопка
  «Положить сюда» в нужной ячейке или колонке (она появляется только при выбранной карточке); Enter/Пробел на
  разложенной карточке возвращает её. Фокус после действия переходит на карточку на новом месте, выбор объявляется
  через `aria-live`. Выбор карточки мышью не включён — мышь и касание работают только перетаскиванием, как раньше.
  Код: `backend/internal/tests/pairing.go`, `common.go` (загрузка, сохранение, оценка), `handlers/tests_routes.go`,
  `attempt_review.go`; фронтенд — `questionTypes.ts`, `PairingEditor.vue`, `TestRunner.vue`.
- **Причина:** просьба владельца 2026-09-29: в `Тест.docx` курса по ИИ есть задания «Соотнесите понятия с
  определениями» и «Классифицируйте полученные ответы», которых в модуле не было (раньше их пришлось разбирать на
  отдельные вопросы с одним вариантом).
- **Следствия:** нужна миграция V13, иначе сохранение формы с новым типом упрётся в CHECK. Тесты второго модуля
  (`/kiosk/tests`, `src/tests/`, `forms*.php`) новые типы не получили. «Соответствие» доступно только в тесте.

## ADR-040. Профиль — «стена ВКонтакте» на сервере

- **Статус:** действует с 2026-10-01
- **Решение:** профиль сотрудника в компоновке старого ВКонтакте, но на семантических токенах портала (цвета,
  шрифт, скругление следуют за темой): слева аватар, действия, «Коллеги» (активные сотрудники того же
  подразделения, 6 штук); справа ФИО, анкета, «Информация» («О себе», «Интересы»), стена. `/profile/:id` —
  профиль коллеги, вход в него — из поиска портала, «Коллег» и имени автора записи.
  Стена на сервере (`profile_wall.php`, V14): писать может любой вошедший сотрудник на любую стену, править —
  только автор, удалять — автор, владелец стены или администратор. Запись — **простой текст** до 4000 символов,
  выводится как текст (`whitespace-pre-line`, без `v-html`): HTML пользователей сервер не хранит, санитайзер
  не нужен. Реакции — те же ключи и компонент, что у новостей (`NewsReactions` с `target="wall"`,
  `wall_post_reactions`). День рождения — из xlsx дней рождения по ФИО (только день и месяц), отдельного поля нет.
  Редактирование — `USlideover` (`ProfileEditSlideover.vue`); настройка темы из профиля убрана — она есть в
  меню шапки.
  Код: `backend/internal/handlers/profile_wall.go`, `profile.go` (`?view=page`), `birthdays.go` (`BirthdayOf`);
  `src/pages/ProfilePage.vue`, `src/components/profile/*`, `src/composables/useProfileWall.ts`.
- **Причина:** просьба владельца 2026-10-01: профиль не нравился, прокрутка была сломана (у `UMain` не было
  `overflow-y-auto`), стена жила только в `localStorage` автора (IMP-03); «хочу, чтобы профиль был как старая
  стена ВКонтакте». Ответы владельца: писать может любой коллега; у записей — реакции как у новостей (без
  комментариев и фото); компоновка VK на токенах портала; в анкете — должность, ОФО, контакты, день рождения,
  «О себе» и интересы.
- **Следствия:** нужна миграция V14, без неё стена отвечает 503 с понятным текстом, а страница профиля
  открывается без «О себе». Форматирование (жирный, списки, эмодзи-меню) из прежнего редактора поста
  ушло — `UEditor` для стены удалён вместе с `wallEditorExtensions.ts` / `wallEditorToolbar.ts`. Записи из
  `localStorage` не переносились. Комментариев и фото в записях нет — это отдельная задача.

## ADR-041. Профиль: данные из учётной записи не редактируются, добавлены желания, награды, курсы, отсутствия

- **Статус:** действует с 2026-10-01
- **Решение:** на портале нельзя менять ФИО, телефон, электронную почту, ОФО и должность. `POST profile.php` пишет
  только `avatar_url`, `about`, `interests` и — **один раз** — `ofo` и `role`: ОФО принимается, пока оно не задано
  (пусто, `-1`, не положительное число), должность — пока пуста или пока не задано ОФО (`planWorkFields`,
  `backend/internal/handlers/profile.go`, тест `profile_test.go`). Остальное сервер молча игнорирует — не 403,
  чтобы онбординг, который шлёт всю карточку, не ломался. Это же закрывает IMP-57: поля, которых нет в теле, не
  затираются. Онбординг блокирует выбор ОФО, если оно уже задано (`UserWorkFields.ofoLocked`). Админка
  (`users.php`) по-прежнему правит всё — исправить ошибку в данных сотрудника может только администратор.
  В профиль добавлены: «Желания» (`profile_wishes`, пишет сам сотрудник, до 20 штук по 200 символов), «Награды»
  (грамоты и достижения, `profile_awards`, выдаёт и удаляет администратор), «Пройденные курсы» (завершённые
  назначения из `course_enrollments`, видят все вошедшие), «Журнал отсутствия» (последние 5 записей —
  те же данные, что любой вошедший читает из `absence_journal.php?user_id=`). Код: `profile.go`
  (`addPageSections`), `profile_extras.go`, `src/components/profile/*`.
- **Причина:** просьба владельца 2026-10-01: «редактировать ФИО, телефон, ОФО, должность, электронную почту на
  корп портале нельзя будет»; в профиле должны быть пройденные обучения и пожелания. Ответы владельца: «пожелания» —
  список желаний сотрудника (как у ВКонтакте); показывать пройденные курсы, журнал отсутствия и «грамоты и
  достижения»; ОФО и должность — один раз при первом входе. Откуда берутся ФИО, телефон и почта после создания
  учётки — **[НЕИЗВЕСТНО]**: `sync.go` только создаёт запись (`ON CONFLICT DO NOTHING`) и обновлять потом не
  умеет, так что менять их теперь может только администратор.
- **Следствия:** нужна миграция V15 (без неё желания и награды отвечают 503, профиль открывается пустыми блоками).
  Награды — только текст (без картинки грамоты); «Выдать награду» видит администратор в режиме «Администратор».
  Пройденные курсы видят все, у чужих без ссылки (назначение чужого не открыть). Сотрудник со ссылкой на уже
  заданное ОФО в онбординге его не меняет — только должность, если она пуста.

## ADR-042. Свой аватар: загрузка фото, квадрат 512×512

- **Статус:** действует с 2026-10-01
- **Решение:** сотрудник может загрузить свою фотографию (`POST /api/profile_avatar.php`, multipart, поле `avatar`).
  Только вошедший и только себе (личность из сессии). JPEG, PNG или WebP до 5 МБ; сервер обрезает по центру до
  квадрата 512×512, заливает прозрачность белым и пишет JPEG `<userID>-<hex>.jpg` в
  `<UPLOAD_DIR>/img/FullPic/avatars/uploads/` (URL `/img/FullPic/avatars/uploads/…`). Фото **сразу** становится
  аватаром (не ждёт «Сохранить»). Файл прежнего загруженного аватара удаляется — и при замене фото, и когда
  `profile.php` меняет аватар на готовый; удаляется только файл этого же пользователя в этой папке
  (`media.RemoveUploadedAvatar`, тест `avatar_test.go`). Свой аватар рисуется на всю рамку (`object-cover`),
  готовые стикеры — с полями (`object-contain`): `isUploadedAvatar()`. Готовые аватары остаются.
  Код: `backend/internal/handlers/profile_avatar.go`, `backend/internal/media/webp.go` (`SaveAvatar`),
  `src/components/profile/ProfileEditSlideover.vue`.
- **Причина:** просьба владельца 2026-10-01 — «добавить возможность загрузить аватар самостоятельно».
  Отдельный эндпоинт, а не `Upload/upload.php`, потому что тот открыт без входа (IMP-61) и режет картинку
  под галерею, не под аватар. Квадрат 512 — чтобы аватар был лёгким (≈10–60 КБ) и ровно ложился в круг и
  квадратные рамки.
- **Следствия:** `/img/FullPic/avatars/` теперь не только стикеры из `.gitignore`: подпапка `uploads/` пишется
  Go API, на сервере её отдаёт то же правило nginx, что и остальные `/img/`. Какой каталог у `/img/` на проде —
  по-прежнему DOC-05 **[НЕИЗВЕСТНО]**: если nginx берёт `/img/` из `public/img/`, а Go пишет в
  `UPLOAD_DIR`, фото не откроются — проверить так же, как загрузку в галерее. nginx: `client_max_body_size 7m`
  для этого пути. Обрезку нельзя настроить (всегда по центру), поворот по EXIF учитывается.

## ADR-043. Встроенный режим темы Nuxt UI отключён (`colorMode: false`)

- **Статус:** действует с 2026-10-02
- **Решение:** в `vite.config.js` плагин `@nuxt/ui` собирается с `colorMode: false`. Тему ведёт только
  `src/composables/useColorMode.ts` (ключ `ui-color-mode`).
- **Причина (подтверждена чтением кода):** `UDashboardSearch` вызывает `useColorMode()` Nuxt UI (vueuse,
  ключ `vueuse-color-scheme`, по умолчанию `auto`) при каждом монтировании. После выхода/входа каркас с
  `UDashboardSearch` монтируется заново, vueuse выставляет на `<html>` системную схему и снимает `dark`,
  а `App.vue` уже смонтирован и `syncFromStorage` повторно не вызывает: в настройках «тёмная», на экране светлая.
  Запуском в браузере не воспроизводилось и не проверялось.
- **Следствия:** `UColorModeButton/Select/Switch` и пункты темы в `UDashboardSearch` не работают
  (в проекте не используются; `:color-mode="false"` в `App.vue` остаётся).

## ADR-044. Курсы: «Не сдан», любое подразделение при назначении, без «Полного описания»

- **Статус:** действует с 2026-10-02
- **Решение:** (1) когда итоговый тест не сдан и у формы включён лимит попыток, а попыток не осталось, Go
  переводит запись в `failed` (`FailIfFinalAttemptsExhausted`, вызывается после завершения попытки;
  `TryCompleteEnrollment` статус `failed` не трогает). Без лимита попытки не кончаются. Вернуть можно только
  «Обнулить результат». (2) Курс назначается на любое подразделение (`useOfoTree.unitItems`, путь «Корень / Отдел»),
  в результатах фильтр и подпись — по точному подразделению; «Включая вложенные» остаётся. (3) Поле
  `fullDescription` убрано из Go и фронтового типа.
- **Причина (подтверждена):** решения владельца 2026-10-02 по Q-08, Q-11, Q-09.
- **Следствия:** число попыток считается по форме и пользователю, как при старте попытки (`tests_routes.go`),
  поэтому «не сдан» наступает ровно тогда, когда старт новой попытки уже запрещён. Колонку
  `course_versions.full_description` не удаляли: её читает и пишет PHP (`api/` не трогаем) — снять её можно
  после отказа от PHP. На прод миграции не нужны. **Вживую не проверено** (только сборка, `go test`, чтение кода).

## ADR-046. Запись на мероприятия и личный календарь — на сервере (V16)

- **Статус:** действует с 2026-10-02
- **Решение:** `event_rsvps` и `calendar_entries` (V16); Go-хендлеры `EventRSVP` (`event_rsvp.php`) и
  `CalendarEntries` (`calendar_entries.php`) в `calendar_personal.go`, оба `requireUser`, личность только из сессии.
  Фронтенд: общий `useEventRsvp.ts` (оптимистичное обновление с откатом, проверка `success`), `useCalendarFeed.ts`
  грузит и пишет записи через API. Три места по CLAUDE.md обновлены: `main.go`, `deploy/nginx-go-api-wave2.conf`, `vite.config.js`.
- **Причина (подтверждена):** решение владельца 2026-10-02 (Q-03). Прежнее хранение в localStorage видело только
  одно устройство.
- **Следствия:** на проде нужна миграция V16 (без неё эндпоинты отвечают 503 с подсказкой). Старые данные из
  localStorage не переносятся: словарь был общий на браузер, владельца отметок не определить; ключи удаляются при
  загрузке модуля. Организатору список записавшихся не показывается (не заказывалось). Проверено вживую на локальной БД:
  curl (изоляция пользователей, идемпотентность, валидация, 401/404/422), интерфейс — запись, откат при ошибке
  сервера, создание записи календаря. Миграция применена дважды (идемпотентна).

## ADR-047. Остаток PHP перенесён в Go; `api/` пока не удалён

- **Статус:** действует с 2026-10-02
- **Решение:** семь PHP-эндпоинтов без Go-аналога перенесены: `course_assignment_cancel`, `course_assignments_list`,
  `course_history`, `course_materials_order`, `courses_archive`, `courses_duplicate`, `courses_readiness`
  (`handlers/courses_extra.go`, `courses/duplicate.go`; три места по CLAUDE.md — `main.go`, nginx wave2, Vite).
  Удаление `api/` не делается в этой задаче: владелец выбрал «только подготовить» —
  [php-decommission.md](php-decommission.md).
- **Причина (подтверждена):** решение владельца 2026-10-02 (Q-02) переносить всё, хотя SPA ни один из семи не
  вызывает (grep по `src/`, `backend/README.md`) — владелец выбрал полный паритет API.
- **Следствия:** Go-версии строже PHP по правам (доступ к категории курса проверяется везде; список назначений без
  фильтра отдаёт только доступные категории). `courses_readiness` использует ту же проверку, что публикация, без
  разбора ответов вопросов. Дублирование теперь копирует варианты «соответствия/классификации» с перепривязкой целей —
  PHP-версия их ломала. Проверено вживую на локальной БД: дублирование курса с 77 вопросами (342 варианта, 31 связь
  «цель») — структура совпала, связи указывают на варианты копии; архив (409/успех/повтор 409), порядок материалов
  (в т. ч. чужой материал не затрагивается), отмена назначения и повтор (409/404), история, список назначений, права
  (401/403). Миграции не нужны.

## Как добавлять запись

1. Решение принято и **видно в коде** — иначе это не ADR, а предложение
   (ему место в [known-issues.md](known-issues.md)).
2. Укажите файл и строку.
3. Причину пишите только подтверждённую. Не уверены — `[НЕИЗВЕСТНО]`.
4. Опишите следствия: что теперь нельзя сделать или о чём нужно помнить.
5. Отменяя решение — не удаляйте запись, пометьте «отменено ADR-NNN».
